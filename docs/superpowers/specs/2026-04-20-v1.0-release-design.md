# Design: ModdersOmni 1.0 Release — Scale, Polish, and BYOK Tiers

**Date:** 2026-04-20
**Status:** Draft (awaiting user review)
**Target version:** v1.0.0 (from v0.9.0)

---

## Overview

ModdersOmni ships a v1.0 milestone covering three work blocks:

- **Block A — Foundation fixes**: five embarrassing audit findings that would block a 1.0 in any reviewer's eyes (broken mobile nav, wizard data loss, broken CPU tier scoring for modern chips, missing storage-drives UI, dev-facing Nexus copy).
- **Block B — Scale architecture**: BYOK-gated modlist size presets (Small 75 → Ultimate 2000 mods) with sub-pass splitting for large phases, plus post-generation disk-space forecasting.
- **Block C — Polish sweep**: ten smaller fixes that raise the perceived polish bar (version step clarity, first-run greeting, tier casing, nav consolidation, preset icons, account deletion, 404 page, sign-out menu, email-verification banner, button copy consistency).

One spec, one implementation plan, one 1.0 release. Internal sequencing is A → B → C for dev order — shared touchpoints (models, components, routes) make splitting into separate specs high-coordination-cost.

### Entitlement model (no Stripe — preserves Apr 9 donation-model decision)

| Preset     | Mod cap   | Requires                                    |
|------------|-----------|---------------------------------------------|
| Small      | ~75       | Any account                                 |
| Medium     | ~150      | Any account (current free ceiling)          |
| Large      | ~500      | BYOK — user-supplied LLM key                |
| Massive    | ~1000     | BYOK                                        |
| Ultimate   | ~2000     | BYOK                                        |

Free tier stays at 150 because 150 is the server-compute budget donations fund. The 500+ tiers are effectively free for ModdersOmni to serve (user's own LLM tokens pay) but remain valuable to the user.

## Block A — Foundation fixes

### A.1 Mobile navigation

**Problem:** At ≤768px viewport, five header links + avatar jam together unreadably.

**Fix:** Hamburger + slide-in drawer at ≤768px. Nav links render in the drawer; avatar + logo stay in the bar.

**Files:** `frontend/src/app/shared/components/header/*` (or wherever the `banner` component lives), plus a small `mobile-nav.component.ts` for the drawer. One new Angular signal for open state. No route changes.

### A.2 Wizard → Settings persistence

**Problem:** Setup wizard captures hardware, but completion does not write to `UserSettings`. A brand-new user lands on Settings → Hardware with empty GPU/CPU fields.

**Fix:** On setup completion (in `playstyle-select.component.submit`), before redirecting to generation, call `PATCH /api/settings/hardware` with the parsed specs including `storage_drives`.

**Backend endpoint:** Already exists — used by the Settings → Hardware → Save button. Reuse.

**Files:** `frontend/src/app/features/setup/steps/playstyle-select/playstyle-select.component.ts` only.

### A.3 CPU tier scoring for modern CPUs

**Problem:** Ryzen 5 7600X → `0/5`. Likely broken for any recent Zen 4, Zen 5, Raptor Lake Refresh, or Arrow Lake CPU.

**Fix:** Update CPU recognition in `backend/app/services/hardware_tier.py` (exact file TBD in implementation plan). Extend the regex/lookup table for:

- **AMD**: Zen 4 (7600/7700/7800X3D/7900/7950 + X/X3D variants), Zen 5 (9600X/9700X/9800X3D/9900X/9950X)
- **Intel**: 13th gen (13600K/13700K/13900K), 14th gen (14600K/14700K/14900K), 15th gen Arrow Lake (Core Ultra 5 245K / Ultra 7 265K / Ultra 9 285K)

Score each family in the same shape as existing entries. Add a unit test exercising 8+ representative CPUs.

### A.4 Storage drives in Settings UI

**Problem:** `user_settings.storage_drives` column exists in the DB and is written by the wizard, but there is no UI in Settings → Hardware to see or edit it later.

**Fix:** Add a "Storage Drives" free-text input in Settings → Hardware tab with a helper tooltip:

> *Paste drive info or list manually — e.g. `C: 180GB free / 931GB, D: 450GB free / 1863GB`. Tip: run `fsutil volume diskfree C:` in PowerShell.*

**Files:** `frontend/src/app/features/settings/settings.component.ts`.

### A.5 Nexus Mods Connection copy rewrite

**Problem:** Current copy is dev-facing: *"Awaiting Nexus Support client registration — this will light up soon."*

**Fix:** Replace with user-facing, transparent copy:

> *"Nexus Collections publishing is coming soon — ModdersOmni is waiting on OAuth app approval from Nexus Mods. We'll light up this section as soon as it's ready."*

Leave section visible (per user preference for transparency). Do not feature-flag hide.

**Files:** `frontend/src/app/features/settings/settings.component.ts`.

## Block B — Scale architecture

### B.1 Preset definition

Five size presets, mapped to a multiplier applied against per-phase `max_mods`:

| Preset     | Target total | Multiplier |
|------------|--------------|------------|
| Small      | ~75          | 0.5×       |
| Medium     | ~150         | 1.0×       |
| Large      | ~500         | 3.3×       |
| Massive    | ~1000        | 6.7×       |
| Ultimate   | ~2000        | 13.3×      |

The multiplier is **not** applied uniformly. Each `ModBuildPhase` gets a new `scale_weight` column (default 1.0) that controls how much it responds to the preset. Foundational phases (Essentials, Compatibility Patches) get `scale_weight ≈ 0.1` — they stay at ~5–10 mods regardless of preset. High-surface phases (Texture Overhauls, NPCs/Creatures, Weather/Lighting) get `scale_weight 2–3` — they absorb most of the scaling budget.

**Effective cap per phase:**

```
effective_cap = round(phase.max_mods × preset_multiplier × phase.scale_weight)
```

Preset seed-values are calibrated so the total across phases lands within 10% of the preset target.

### B.2 Sub-pass splitting

**Rationale:** Past ~25 sequential `add_to_modlist` tool calls, LLM conversation context bloats and quality degrades (repetition, laziness). Past ~50, even Gemini Flash's effective context gets uncomfortable.

**Solution:** When a phase's `effective_cap > 25`, split it into N sub-passes where each sub-pass is capped at 25 mods. Each sub-pass starts with **fresh LLM context** — no prior tool-call conversation history — but sees a compact "already added" summary in its system prompt.

**Per-phase loop shape (revised `pipeline.py`):**

```python
async def run_phase(phase, session, preset_multiplier):
    effective_cap = round(phase.max_mods * preset_multiplier * phase.scale_weight)
    sub_pass_count = max(1, math.ceil(effective_cap / 25))
    per_sub_pass_cap = math.ceil(effective_cap / sub_pass_count)

    for sub_pass_index in range(sub_pass_count):
        already_added = session.modlist_entries_for_phase(phase.id)
        sub_pass_guidance = phase.sub_pass_guidance[sub_pass_index] if phase.sub_pass_guidance else None

        await run_single_sub_pass(
            phase=phase,
            cap=per_sub_pass_cap,
            already_added=already_added,   # compact summary, injected in prompt
            guidance=sub_pass_guidance,    # optional phase-specific hint per sub-pass
        )

    # Gemini Pro reviewer runs ONCE per phase, not per sub-pass
    await reviewer.review_phase(phase, session)
```

**Already-added summary format** (injected into each sub-pass prompt): a bullet list of `- {name} by {author}` — not full tool-call history. Keeps context small while preventing duplicates.

**`sub_pass_guidance` field** (optional): per-phase hints that steer each sub-pass to a different sub-topic. Example for the Texture Overhauls phase at Large preset (5 sub-passes of 25):

```json
[
  "Focus on landscape and terrain textures first.",
  "Now emphasize architecture and static mesh improvements.",
  "Next: armor, weapon, and clothing textures.",
  "Now: NPC body, face, and hair textures.",
  "Finally: creature, clutter, and miscellaneous textures."
]
```

For phases with no `sub_pass_guidance`, each sub-pass just receives "add up to N more mods, avoiding duplicates from the already-added list."

### B.3 Nexus API throttling

At Ultimate preset (~2000 mods), we'll issue ~6000 Nexus GraphQL calls per generation. The current `NexusModsClient()` fires without client-side throttling.

**Fix:** Add an `asyncio.Semaphore(8)` to `NexusModsClient` to cap concurrent in-flight requests. 8 is arbitrary but defensive — Nexus Support has not given us explicit rate limits on the unauthenticated v2 endpoint. Make the semaphore size configurable via env var `NEXUS_CONCURRENCY` (default 8).

**Files:** `backend/app/services/nexus_client.py`.

### B.4 Disk-space forecasting (post-generation only)

Per our Section 3 discussion: **no pre-generation estimate, no Generate-button warning modal.** Disk-space information appears only:

1. **During generation** — running total in the SSE viewer header: *"47 mods added · 12.3 GB so far"*
2. **After generation** — summary card on the completed modlist page

**Post-generation card copy:**

Comfortable fit:
> *Total: 84 GB download / ~210 GB installed. Largest free drive: **D: 450 GB** ✓ Comfortable fit.*

Tight fit:
> *Total: 180 GB / ~450 GB installed. Largest free drive: **C: 180 GB** ⚠ You'll need to free ~270 GB (or install to a different drive) before the modlist will fit.*

**Installed-size multiplier:** Flat 2.5× on download bytes. Accurate enough for Bethesda modding; tunable later.

**Sized vs unsized handling:** If Nexus does not return `sizeInBytes` for an entry (rare; older mods), store NULL and report honestly: *"47 sized · 3 unsized — estimate may be conservative."*

**No storage_drives captured:** If user has not entered drive info, show the size totals without the comparison bar, plus a prompt: *"Add your drive info in Settings to see if this fits."*

### B.5 Dashboard in-progress badge + email on completion

These two small additions turn the cross-device (phone → PC) workflow from "technically supported" into first-class.

**In-progress badge (Dashboard):** Modlist cards display one of three states:
- **In progress** — badge with a pulsing dot, subtitle "{phase} of {total} — {elapsed}"
- **Complete** — default state with size/date
- **Failed/paused** — badge with error icon, one-line message

Status comes from the existing `GenerationManager` singleton (already tracks in-memory state per modlist); frontend polls `GET /api/generation/{id}/status` every 15s while any in-progress card is visible.

**Email on completion:** When a generation pipeline completes successfully (or fails with a terminal error), send an email to `user.email`:

- Success subject: *"Your {game} modlist is ready"*
- Success body: plaintext + HTML with a link back to the modlist page and a summary line (N mods, X GB download)
- Failure subject: *"Your {game} modlist generation ran into a problem"*

Controlled by a new key `email_on_generation_complete` in the existing `user_settings.notification_prefs` JSON column (no schema change). Default **true** for new users; user can turn off at any time via **Settings → Notifications**, which must show a labeled toggle:

> **Email me when generation finishes** — *Get a notification when your modlist is ready, so you can start from your phone and finish on your PC.*

Reuses the same SMTP path as email verification (existing infra). Sends regardless of `user.email_verified` — verification is for account security, not notification delivery; we nudge verification separately via the banner in C.10.

**Files:** `backend/app/services/generation/pipeline.py` (terminal-state hook), new `backend/app/services/email/generation_complete.py`, `frontend/src/app/features/dashboard/dashboard.component.ts`.

### B.6 New SSE event type

Add a new event type `size_update` emitted each time `add_to_modlist` fires. Payload:

```json
{ "type": "size_update", "total_bytes": 12958294844, "mod_count": 47 }
```

Frontend generation viewer listens and updates the running-total pill in the header.

### B.7 DB schema changes (migrated via Alembic — see §Migration Strategy)

| Table              | Column              | Type       | Default | Notes                              |
|--------------------|---------------------|------------|---------|------------------------------------|
| `modlist_entries`  | `file_size_bytes`   | BIGINT     | NULL    | Captured from Nexus on add         |
| `mod_build_phases` | `scale_weight`      | FLOAT      | 1.0     | Per-phase response to preset mult. |
| `mod_build_phases` | `sub_pass_guidance` | JSON       | NULL    | Optional per-sub-pass steering hints |

### B.8 New backend endpoints

- `GET /api/modlist/{id}/size-summary` → returns `{ download_bytes, installed_estimate_bytes, sized_count, unsized_count, largest_drive_free_bytes | null, fit_status: "comfortable" | "tight" | "insufficient" | "unknown" }`

### B.9 Scope boundary: no Stripe, no paywall

The Apr 9 donation-model decision stands. Gating is by BYOK presence only:

```python
if preset in ("Large", "Massive", "Ultimate") and not request.llm_credentials:
    raise HTTPException(
        status_code=402,
        detail="This modlist size requires your own LLM API key. See Settings > AI Providers.",
    )
```

(402 Payment Required is the semantic fit here, even though no actual payment is due — the BYOK key is the "payment".)

### C.6 Preset icons

- Vanilla+ → `sparkles`
- Survival → `tent`
- Combat → `swords`
- Magic → `wand-2`

- Immersion → `drama`

### C.7 Account deletion
New "Danger Zone" section at the bottom of Settings > Profile:

- Red **Delete Account** button
- Confirmation modal — type `DELETE` exactly to unlock submit
- Backend: `DELETE /api/user/me` — cascades via existing FK relations. Requires a password re-prompt for users with a password credential; OAuth-only users get a separate confirmation text.

### C.8 404 error page

### C.9 Sign-out menu
Avatar button (top-right, e.g. "CT") currently doesn't visibly do anything useful. Wire it to a dropdown menu:
- **Settings** → `/settings`
- **Sign out** → clears JWT, redirects to `/`

### C.10 Email-verification banner
Add a dismissable top-of-app banner for users whose email is not yet verified:

> *Verify your email to secure your account.* **[Resend verification link]**

Banner hides permanently once verified or dismissed (localStorage-gated).

## Migration strategy — adopt Alembic

CLAUDE.md notes Alembic is installed but unused; schema is currently managed via `Base.metadata.create_all` in `main.py`'s lifespan. **1.0 is the right moment to adopt Alembic.**

### Why Alembic now

- Block B adds three new columns to existing tables. `create_all` only creates missing tables; it does NOT alter existing ones. Without migrations, production will silently be missing `file_size_bytes`, `scale_weight`, `sub_pass_guidance`.
- Long-term cost of NOT adopting compounds — every new column in v1.1, v1.2 carries the same risk.

### Plan

Alembic is already scaffolded in `backend/alembic/` with `env.py`, `versions/`, and `alembic.ini` — it's installed but never exercised. The 1.0 migration begins using it.

1. Generate a baseline migration reflecting current production schema: `alembic revision --autogenerate -m "baseline_v0.9.0"`. Review the generated script — autogenerate may drift on enums, JSON, or UUID types specific to this codebase; hand-fix as needed.
2. Apply baseline to production (`alembic stamp head` — marks the current schema as already at this revision without re-running DDL).
3. Generate the 1.0 migration: `alembic revision --autogenerate -m "v1.0_scale_and_sizes"` — autogenerate should pick up the three new columns on `modlist_entries` and `mod_build_phases`. Review and hand-fix as needed.
4. On deploy, `alembic upgrade head` runs in Render's pre-deploy hook (or as an early step in the lifespan startup before `run_seed.py`).
5. Remove `Base.metadata.create_all()` from `main.py` — migrations become the single source of truth.
6. Update CLAUDE.md to reflect Alembic as the active migration system.

### Seed compatibility

`run_seed.py` remains the source of truth for phase content, including new `scale_weight` and `sub_pass_guidance` values for each phase. Re-running seed on an existing database must be idempotent (existing records UPDATE in place; new columns populate correctly).

### Rollback

Each migration ships with a matching `downgrade()` implementation. Production rollback = `alembic downgrade -1`.

## Success criteria

The 1.0 release is ship-ready when:

1. A fresh user on `Cindysal9695@gmail.com` can complete the Playwright walkthrough on both 1440px and 390px viewports without hitting any blocker-class issue
2. All CI hard gates pass (`ruff`, `pytest`, `ng build`)
3. The 2026-04-09 donation-model decision is not violated (no Stripe package, no subscription endpoints)
4. Alembic migrations apply cleanly on a baseline-stamped v0.9.0 database
5. A BYOK user can successfully generate a Large (500-mod) Skyrim modlist in under 25 minutes wall time with their own Gemini Flash + Groq keys
6. Dashboard in-progress badge appears within 15s of generation start
7. Email on completion lands in the user's inbox for both success and failure cases
8. The donation links (Ko-fi, Patreon) on `/support` remain functional — this is NOT a paywall release
